## 2. Plant the Vault secret

The cron jobs read `phase6_cron_secret` from Supabase Vault at fire time. The
worker route validates the header against the Vercel `CRON_SECRET` env. Both
must hold the same value.

Run once via Supabase MCP `execute_sql` or the dashboard SQL editor:

```sql
SELECT vault.create_secret(
  '<32-char-secret-matching-Vercel-CRON_SECRET-env>',
  'phase6_cron_secret',
  'X-Cron-Secret header value for /api/internal/recap-email/run'
);
```

**Generate a fresh secret if needed:**
```bash
# pick one
openssl rand -hex 32
# or
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

**The same secret must be set as `CRON_SECRET` in Vercel** (see step 3) —
this is intentional shared with Phase 5's digest cron secret so a single
rotation covers both surfaces. If Phase 5 already set `CRON_SECRET` you can
reuse the same value rather than picking a new one.

**Verify:**
```sql
SELECT name, created_at FROM vault.secrets WHERE name = 'phase6_cron_secret';
-- 1 row
```

## 5. Smoke-test the recap-email worker

Manually trigger each mode with the matching `CRON_SECRET`:

```bash
SECRET=$(pnpm vercel env pull --environment=production --yes /dev/stdout | grep CRON_SECRET | cut -d= -f2- | tr -d '"')

# Annual preview — sends recap email to all cadence in (daily, weekly, monthly)
curl -X POST https://ploxa.vercel.app/api/internal/recap-email/run \
  -H "Content-Type: application/json" \
  -H "X-Cron-Secret: $SECRET" \
  -d '{"mode":"annual_preview"}' \
  -i

# Expected: 200 OK with JSON body {sent, failed, skipped, candidates, mode}
# If candidates=0: all eligible users have last_recap_sent_at < 20h ago, or
# no users with cadence != 'never' exist. That's a valid pass.
```

**Negative test — confirm the gate:**
```bash
curl -X POST https://ploxa.vercel.app/api/internal/recap-email/run \
  -H "Content-Type: application/json" \
  -H "X-Cron-Secret: nope" \
  -d '{"mode":"annual_preview"}' \
  -i

# Expected: 404 (not 401) — the route hides its existence on auth fail.
```

**If 5xx returns:** check Vercel runtime logs for the deployment.

## 6. Verify cron jobs fire

The next scheduled tick is the **1st of next month at 12:00 UTC** for the
monthly cron. Annual previews fire **Dec 1 at 12:00 UTC**. To verify
end-to-end without waiting, manually trigger via curl (step 5) and inspect
`profiles.last_recap_sent_at` timestamps after.

To trigger the schedule manually via pg_cron for a one-time test:
```sql
-- Inspect when each job last ran:
SELECT jobname, last_run_started_at, last_run_finished_at
FROM cron.job j
LEFT JOIN cron.job_run_details d ON d.jobid = j.jobid
WHERE jobname LIKE 'phase6-%'
ORDER BY jobname, last_run_started_at DESC NULLS LAST;
```

## Notes / gotchas

- The Vercel cron-list will populate immediately on migration apply but
  jobs silently 404 against the worker if `phase6_cron_secret` isn't set.
  Order: migrations → Vault secret → env var → deploy → smoke-test.

- `cacheOrBuildYearly` and `cacheOrBuildMonthly` are the only two paths
  that write recap rows. Email worker uses them as pre-warm. Page views
  use them as cache-or-build. They share the same UPSERT semantics.

- AI captioning fails open: if the router throws or returns malformed
  JSON, captions fall back to deterministic templates and `ai_calls`
  logs a `success=false` row. The user-facing recap renders either way.

- The Phase 5 digest worker and Phase 6 recap worker share `CRON_SECRET`
  and `RESEND_API_KEY` but not their from address — both use
  `RESEND_DIGEST_FROM_ADDRESS` because there's no separate recap-from env.
  If you want to use a different from address for recaps, add
  `RESEND_RECAP_FROM_ADDRESS` env + update
  `app/api/internal/recap-email/run/route.ts`'s fallback chain in a follow-up.
