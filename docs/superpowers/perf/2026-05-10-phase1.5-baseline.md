## Surface 1: /library

### Static-analysis findings

**TanStack Query on mount (Suspect A)**

File: `components/library/library-view-switcher.tsx:45-49`

```ts
const { data: items = initialData } = useQuery({
  queryKey: ["library", filter, sort],
  queryFn: () => getUserLibrary({ status: filter, sort }),
  initialData: filter === initialFilter && sort === initialSort ? initialData : undefined,
});
```

The library page is a Next.js Server Component that calls `getUserLibrary()` at request
time and passes the result as `initialData` into `LibraryViewSwitcher`. The QueryClient
default in `app/providers.tsx:15` is `staleTime: 30_000` (30 seconds). This means:

- On first mount, if `filter === initialFilter && sort === initialSort`, the query sees
  `initialData` **and** TanStack marks it with `dataUpdatedAt = 0` (the sentinel for
  "data provided externally, timestamp unknown"). With `staleTime: 30_000`, the library
  query fires a refetch immediately on mount because `dataUpdatedAt = 0` makes the data
  appear perpetually stale.
- Result: every cold `/library` page load triggers two round-trips — one server-render
  that already ran `getUserLibrary()`, then a second identical `getUserLibrary()` call
  from TanStack right after hydration. For a user with 200+ logs this is a wasted
  server-action round-trip + re-render on every visit.
- If filter/sort differ from the initial values (user changed them before hydration
  completes, which is unlikely but possible), `initialData` is `undefined` and TanStack
  fetches normally.

**Fix path:** Set `initialDataUpdatedAt: Date.now()` on the `useQuery` call so TanStack
treats the server-rendered data as freshly fetched. The 30 s `staleTime` will then
prevent a redundant refetch on mount for 30 seconds. See Task 15 for implementation.

**next/image unoptimized usage (Suspect B)**

`next.config.ts:5` already has `media.rawg.io` in `remotePatterns`:

```ts
images: {
  remotePatterns: [{ protocol: "https", hostname: "media.rawg.io" }],
},
```

Despite this, all Image consumers in the library path use `unoptimized`:

| File | Component | Context |
|------|-----------|---------|
| `components/library/library-poster.tsx:33` | `LibraryPoster` | Shelf view — main grid |
| `components/library/library-list.tsx:50` | `LibraryList` | List view — row thumbnails |
| `components/library/status-stacks.tsx:77` | `StatusStacks` | Stacks view — horizontal scroller |

`LibraryPoster` is the highest-volume Image consumer: the shelf grid renders one
`<Image fill sizes="(max-width: 640px) 50vw ..." unoptimized />` per game. With
`unoptimized`, Next.js bypasses its image pipeline entirely: no WebP conversion, no
responsive-size negotiation via srcset, no blur placeholder. Full-resolution RAWG JPEGs
(typically 600 × 900 px, 60-150 KB each) are shipped to the browser unchanged.

A user with 50 logged games loading the shelf view in one viewport scroll downloads
approximately 50 × ~80 KB = ~4 MB of unoptimized JPEG. After dropping `unoptimized`, the
Next.js optimizer serves WebP at the width dictated by `sizes` — ~140 px wide on desktop
— reducing each image to roughly 5-15 KB. Estimated payload saving: 80-90% on image bytes.

## Surface 2: /dashboard (routes to /home)

Note: `/dashboard` immediately redirects to `/home` via
`app/(app)/dashboard/page.tsx:3`. The real dashboard is
`app/(app)/_cockpit/cockpit-dashboard.tsx`.

### Static-analysis findings

**In-memory aggregation in `getUserStats` (Suspect C)**

File: `lib/logs/server-actions.ts:224-257`

```ts
export async function getUserStats(): Promise<UserStats | null> {
  const rows = await db
    .select({ status: schema.logs.status, rating: schema.logs.rating })
    .from(schema.logs)
    .where(eq(schema.logs.userId, user.id));

  // Then iterates all rows in JS:
  for (const r of rows) {
    byStatus[r.status as LogStatus]++;
    if (r.rating != null) { ratingSum += Number(r.rating); ratingCount++; }
  }
}
```

`getUserStats` selects **every log row** for the current user and aggregates them in Node
process memory. For a user with N logs this means:
- N row objects allocated on the heap (each containing `status` + `rating` strings)
- Linear JS loop for counting and summing
- Full N-row result set transmitted over the Supabase/Postgres connection

The equivalent computation can be done entirely in Postgres with `COUNT(*) FILTER
(WHERE status = ...)` and `AVG(rating::numeric)`, returning a single aggregate row
regardless of library size. At 100 logs the difference is negligible; at 1000+ logs the
heap pressure and network payload become measurable.

**`getRecentActivity` — correctly bounded**

File: `lib/logs/server-actions.ts:269-300`

`getRecentActivity` uses `.limit(limit)` (default 10) and does no in-memory aggregation;
it only maps the 10 returned rows. This function is **not a performance concern**.

**Dashboard makes three parallel server-action calls**

File: `app/(app)/_cockpit/cockpit-dashboard.tsx:11-15`

```ts
const [library, stats, activity] = await Promise.all([
  getUserLibrary({}),
  getUserStats(),
  getRecentActivity(10),
]);
```

The three calls are correctly parallelised with `Promise.all`, so they don't serialize.
However:

1. `getUserLibrary({})` fetches ALL logs (no status filter) to power `StatusStacks` and
   the greeting context. This is the same full-scan `getUserStats` triggers. On dashboard
   load, the user's entire log table is read **twice**: once for library items (with game
   JOIN) and once for the stats aggregation. A view or a single combined query could
   collapse this.

2. The dashboard is a Server Component with no client-side caching — it re-fetches on
   every navigation to `/home`. There is no TanStack Query wrapper here, so no
   `staleTime` benefit applies; every visit is a cold server render.

## Surface 3: ⌘K palette (command palette)

### Static-analysis findings

**Palette architecture**

File: `components/palette/command-palette.tsx`

The palette is a Zustand-store-driven overlay. On open it renders `GameSearchResults`
(search mode) or `QuickLogForm` (log mode). It does **not** fetch any data on open — it
waits for the user to type at least 2 characters before firing a search.

**Debouncing in `GameSearchResults`**

File: `components/palette/game-search-results.tsx:16` and `lib/palette/use-debounced.ts`

```ts
const debouncedQuery = useDebounced(query, 250);
const { data: results = [], isLoading } = useQuery({
  queryKey: ["palette-search", debouncedQuery],
  queryFn: () => searchGames(debouncedQuery),
  enabled: debouncedQuery.length >= 2,
  staleTime: 1000 * 60 * 5,   // 5 minutes
});
```

`useDebounced` is a custom hook that delays propagation of the query by 250 ms using
`setTimeout` / `clearTimeout`. The TanStack `staleTime` for palette results is 5 minutes
— search results for the same query string are re-used from cache for 5 minutes without
a refetch.

This is well-implemented:
- No fetch fires until 250 ms of keypress silence (prevents per-keystroke hammering of
  the RAWG API)
- 5-minute cache means repeated searches for the same game title skip the network
- `enabled: debouncedQuery.length >= 2` prevents single-char fetches

**Cover images in search results**

File: `components/palette/game-search-results.tsx:128`

```ts
<Image src={url} alt={alt} fill sizes="36px" className="object-cover" unoptimized />
```

The same `unoptimized` issue applies here, but the impact is smaller: results list shows
at most ~20 thumbnails, each at 36 px display width. Even at full RAWG resolution that is
a manageable payload (~1-3 MB total), but it's still unnecessary overhead given that
`media.rawg.io` is already in `remotePatterns`.

**`QuickLogForm` cover image**

File: `components/palette/quick-log-form.tsx:90`

Also uses `unoptimized` for the selected game's cover in the log form. Single image,
minimal impact.

**No per-keystroke server calls**

Unlike a naive typeahead, the palette does not fire a server action per character typed.
The 250 ms debounce + TanStack caching makes this surface the least concerning of the
three for server-side load.

## Suspects examined (cross-cut)

### Suspect A: TanStack Query stale refetch on /library mount

**Finding:** `app/providers.tsx:15` sets `staleTime: 30_000`. However,
`components/library/library-view-switcher.tsx:45-49` passes `initialData` from the
server render without setting `initialDataUpdatedAt`. TanStack treats `initialData`
supplied this way as having `dataUpdatedAt = 0`, making it perpetually stale regardless
of `staleTime`. The query fires a redundant background refetch immediately after
hydration on every cold page load.

**Impact estimate:** Medium. The refetch is a background operation — it does not block
render or cause a loading spinner. However it creates a server-action round-trip that
duplicates the SSR work, generates a second DB query under load, and can cause a brief
flicker if the refetched data differs from the server-rendered data (e.g. a log was
added in another tab). For users with large libraries (200+ entries) the refetch
response latency is also meaningful.

**Fix complexity:** Low. One-line addition: `initialDataUpdatedAt: Date.now()` on the
`useQuery` call in `library-view-switcher.tsx`.

---

### Suspect B: next/image unoptimized

**Finding:** `next.config.ts:5` correctly lists `media.rawg.io` in `remotePatterns`, so
the Next.js image optimizer can handle RAWG URLs. Despite this, six `<Image>` consumers
in production code use `unoptimized`:

| File | Display size | Volume |
|------|-------------|--------|
| `components/library/library-poster.tsx:33` | 50-140 px wide | High — one per game in shelf |
| `components/library/library-list.tsx:50` | 48 px | High — one per game in list |
| `components/library/status-stacks.tsx:77` | ~80 px | Medium — up to 12 per status bucket |
| `components/palette/game-search-results.tsx:128` | 36 px | Low — max ~20 results |
| `components/palette/quick-log-form.tsx:90` | ~80 px | Negligible — single image |
| `components/game/game-detail.tsx:37` | Large hero | Medium — single image per game page |

`library-poster.tsx` is the critical path: the shelf view renders every logged game as a
poster. Dropping `unoptimized` and letting Next.js serve WebP at the appropriate
responsive breakpoint reduces per-image transfer from ~60-150 KB to ~5-15 KB.

**Impact estimate:** High (for `/library`). This is the single largest optimization
opportunity by byte count. Mobile users on `/library` with 50+ games currently download
several MB of unoptimized JPEG. LCP is directly gated by the first poster's image load.

**Fix complexity:** Low. Remove `unoptimized` from the six consumers. The domain config
is already in place — the pipeline is ready to activate.

---

### Suspect C: In-memory aggregation in getUserStats

**Finding:** `lib/logs/server-actions.ts:231-256` selects all `(status, rating)` pairs
for the user and iterates them in Node.js to produce counts and averages. For N logs this
is O(N) memory and O(N) JS work on the server per dashboard load.

`getRecentActivity` (lines 269-300) is **not** a concern — it uses `.limit()` and does
no in-memory aggregation beyond a simple `.map()` on 10 rows.

The dashboard also calls `getUserLibrary({})` in the same `Promise.all`, which fetches
all log rows again (with a games JOIN). So on each `/home` load, the user's entire logs
table is read twice from Postgres — once for the library, once for stats.

**Impact estimate:** Low to Medium. At typical early-user scale (< 500 logs), the
in-memory work is fast (< 1 ms JS, < 50 KB heap). At power-user scale (1000+ logs) or
under concurrent load from multiple users, the repeated full-table reads become
meaningful. The double-read of the logs table on dashboard load is wasteful regardless
of scale and is the stronger argument for fixing this.

**Fix complexity:** Medium. The stats query can be rewritten to use Drizzle's `count()`
and `avg()` with `groupBy(schema.logs.status)`, returning one aggregate row per status.
The double-read can be addressed by computing stats from the already-fetched library
array in the server component, eliminating the second DB round-trip entirely.

## Ranked priority for Task 15

**1. Suspect B — Drop `unoptimized` from library Image consumers (High impact, Low complexity)**

The RAWG domain is already in `remotePatterns`. This is a pure deletion: remove
`unoptimized` from `library-poster.tsx`, `library-list.tsx`, and `status-stacks.tsx`.
Estimated payload saving: 80-90% reduction in image bytes on `/library`, directly
improving LCP and reducing mobile data cost. No architecture changes required.

**2. Suspect A — Add `initialDataUpdatedAt` to the library query (Medium impact, Low complexity)**

One-line fix that eliminates the redundant post-hydration server-action call on every
`/library` visit. Reduces duplicate DB load and removes a potential render inconsistency.
Do this immediately after Suspect B since it requires reading `library-view-switcher.tsx`
anyway.

**3. Suspect C — Eliminate double log-table read on dashboard (Medium impact, Medium complexity)**

Compute stats from the already-fetched `library` array in `cockpit-dashboard.tsx`
instead of making a separate `getUserStats()` call. This removes one full-table DB scan
on every `/home` load without changing the public API surface. The deeper DB-side
aggregation rewrite (GROUP BY in SQL) is a nice-to-have for scale but not urgent at
current user counts.

**4. Suspect B (palette) — Drop `unoptimized` from palette Image consumers (Low impact, Low complexity)**

`game-search-results.tsx` and `quick-log-form.tsx` also use `unoptimized`, but at small
display sizes (36-80 px) and low volumes (≤ 20 images). Fix these alongside Suspect B
above for completeness — it's the same code pattern, same fix.

**Skip (non-issue): palette debounce / caching**

The palette's 250 ms debounce and 5-minute `staleTime` are already well-tuned. No work
needed here. The open latency is dominated by the 150 ms Framer Motion animation, not
data fetching.

## Applied fixes (Task 15)

The fixes below were applied in priority order from the ranked list above. Each is a
separate commit so the impact of each can be attributed independently.

### Fix 1 — Drop `unoptimized` from all 6 Image consumers
**Commit:** `7a40cb4` (Phase 1.5.15a)

Removed the `unoptimized` prop from:
- `components/library/library-poster.tsx`
- `components/library/library-list.tsx`
- `components/library/status-stacks.tsx`
- `components/palette/game-search-results.tsx`
- `components/palette/quick-log-form.tsx`
- `components/game/game-detail.tsx`

Empirical re-measure (TBD): network-transfer bytes filtered to `media.rawg.io` on a cold
`/library` load. Static analysis predicts 80-90% byte reduction.

### Fix 2 — Mark `/library` initialData as fresh
**Commit:** `d1e74d8` (Phase 1.5.15b)

Added `initialDataUpdatedAt: Date.now()` to the library `useQuery` in
`components/library/library-view-switcher.tsx` so the SSR-provided `initialData` is not
treated as stale. The 30s `staleTime` now suppresses the redundant post-hydration
`getUserLibrary()` call.

Note: `Date.now()` inside a client component render triggers the `react-hooks/purity`
ESLint rule. The call is intentional here — it records the hydration timestamp, not a
reactive value — and is suppressed with a targeted `eslint-disable-next-line` comment
matching the pattern used elsewhere in the codebase (e.g. `cockpit-dashboard.tsx:19`).

Empirical re-measure (TBD): count of `getUserLibrary` requests visible in the Network tab
on a cold `/library` load. Static analysis predicts a drop from 2 to 1.

### Fix 3 — Compute dashboard stats from the library array
**Commit:** `3d81bac` (Phase 1.5.15c)

Replaced `getUserStats()` in `cockpit-dashboard.tsx` with `computeUserStatsFromLibrary()`,
a local helper that iterates the already-fetched `library` array. The dashboard now
performs one logs-table read per `/home` load instead of two.

The helper produces the exact same `UserStats` shape (`{ total, byStatus, averageRating }`)
as `getUserStats()`, including the `Math.round(... * 10) / 10` rounding for `averageRating`.
Since the local computation always returns a value (not `null`), the `{stats && <StatsStrip>}`
conditional guard was simplified to `<StatsStrip stats={stats} />`.

Empirical re-measure (TBD): server log shows one fewer Postgres query per `/home` load.
The `getUserStats` server action remains exported for other potential callers.

### Skipped (non-issues)

**Palette debounce / caching** — 250 ms debounce + 5-minute `staleTime` are well-tuned.
No work needed.

**Server-side `GROUP BY` rewrite of `getUserStats`** — at current user scale the JS
iteration is fast. The doubled-scan was the bigger waste, addressed by Fix 3. A proper
SQL aggregation can be added later if scale demands it.

### Follow-up bundle observations (from autonomous parse)

Things worth keeping in mind for any future bundle pass — none urgent:

- **`framer-motion` at 139.8 KB parsed** is the largest non-framework dep.
  Tier 5 of the spec deliberately keeps this for the spring-physics morph
  and palette overlays. If a future direction softens the UX-invariance
  constraint, replacing entry animations with CSS could free ~30 KB gzip.
- **`@radix-ui/react-dropdown-menu` at 49.5 KB parsed** is the heaviest
  Radix package in use. `optimizePackageImports` is already active for it.
  No further win available without dropping Radix entirely.
- **`floating-ui` at 49.8 KB in a single chunk** is pulled in transitively
  by Radix popovers/menus. Sharing across consumers means it's not
  separately optimizable — it sits with Radix.
- **`sonner` at 32.8 KB** is the toast library (success/error toasts from
  log actions, avatar uploads). Could be replaced with a lighter
  alternative if toasts ever become a bundle hot spot, but at 9 KB gzip
  it's a reasonable cost for the polish.
- **`<app code>` at 119.7 KB** is the cumulative cost of all 12 routes +
  components + lib. Modest for a Next 16 app at this stage.
