# Phase 1.5 — Polish design

## Context

Phase 1 (core logging) passed its 14-check manual gate on 2026-05-10 (tag `phase-1-complete`, commit `d4618f5`). The end-to-end log roundtrip works (sign-in → ⌘K → search → quick-log → toast → cockpit/library reactivity → detail panel → edit). The user flagged six polish items afterward; this spec covers those plus one carry-in refactor surfaced during Step A branch triage:

1. **Performance** — measurable interaction lag (suspects: TanStack Query `initialData` always-stale refetch, `unoptimized` `next/image`, in-memory aggregation in `getUserStats` / `getRecentActivity`)
2. **Navigation UI** — no primary nav (user had to type `/library` manually)
3. **View rename** — `grid` → `Shelf`; `shelf` → `Stacks`
4. **Username at signup** (currently auto-derived from email)
5. **Heart visuals** — upper-fill of half/full hearts reads as unfilled
6. **Branch triage** — handled in Step A (5 commits landed on main; 7 branches deleted; 7 worktrees deregistered)
7. **(new) Mapper-dedup** — extract `mapRowToLibraryItem` with all current fields, applied to all 4 sites. Replaces the `claude/elegant-margulis-62618a` branch (dropped because cherry-picking would have regressed three Phase 1.31 fields — `platformPlayedOn`, `isReplay`, `isPrivate` — at two sites and only deduplicated 2 of 4 inline mapper sites).

During item-2 brainstorming the user expanded scope to include a full **profile-picture (PFP) upload feature** with hover-only GIF playback, hosted on a new `/settings` page.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Nav placement | Top-bar tabs in existing header | Matches existing layout; minimal new surface; mirrors Letterboxd |
| Mobile nav | Hamburger → shadcn `<Sheet>` drawer | Lowest mobile real estate cost; familiar pattern |
| Right-side header | Profile dropdown with avatar + initials fallback | Sets up for PFPs; consolidates email + logout |
| PFP scope | Bundled into Phase 1.5 (full upload feature, not scaffold) | User intent: real product feel, not placeholder |
| GIF playback | Hover/focus only (static frame at rest); honors `prefers-reduced-motion` | Avoids motion-sickness, CPU drain in nav |
| Upload UI host | New `/settings` page with section-based layout | Settings hub will be needed eventually; build it once |
| Storage backend | Supabase Storage bucket `avatars`, public-read | Already in stack; built-in RLS |
| Cropping | `react-easy-crop` modal for static images; GIFs upload as-is | Polished UX without GIF re-encoding complexity |
| Max upload | 5 MB | Covers most images + short GIFs |
| Initials fallback | 1 char + bg color from `hash(userId)` against pixel-art palette | Looks intentional |
| View rename | Pixel-art = `Shelf`; status carousels = `Stacks` | Distinctive pairing; doesn't conflict with existing `_cockpit/` |
| Username validation | Live (debounced 300ms) + on-submit safety check | Polished pattern (Letterboxd / Bluesky); cheap endpoint |
| Username constraints | 3–24 chars, lowercase + digits + underscores | URL-safe; route-collision-safe |
| Username editing | Always editable from `/settings` | Friendlier; covers existing email-derived users |
| Username field model | One field for both URL handle + display name | Can split later if needed |

## Architecture

### A. Navigation & header

A new shared `<AppHeader />` component replaces the inline header currently in `app/(app)/layout.tsx`.

**Desktop layout (≥768px):**
`logo · NavTabs(Home/Library/Profile) · search · ProfileDropdown(avatar)`

**Mobile layout (<768px):**
`logo · compact-search · hamburger ☰`. The hamburger opens a shadcn `<Sheet />` slide-in drawer containing: Home, Library, Profile, **Settings**, divider, `@username`, email, "Log out" button.

**Active tab indication:** underline + theme primary accent color (the existing accent token used by the rest of the UI; implementation reuses it rather than introducing a new value). Computed client-side via `usePathname()` (header is a client component for interactivity).

**Tab routing:**
- `Home` → `/home`
- `Library` → `/library`
- `Profile` → `/u/[currentUserUsername]` — same view other users see, no separate "edit mode." The Profile dropdown's "Settings" link is where editing happens. (Avoids adding a `/profile` route just to redirect.)

**Profile dropdown (desktop):** shadcn `<DropdownMenu />` triggered by the avatar circle. Menu items: `Logged in as @username` (read-only), email (read-only), "Settings" link (`/settings`), "Log out" button.

**Components:**
- `components/layout/app-header.tsx` — composes everything; receives the user from server-rendered layout
- `components/layout/nav-tabs.tsx` — Home/Library/Profile, derives active state from `usePathname()`
- `components/layout/mobile-menu.tsx` — hamburger trigger + Sheet drawer contents
- `components/layout/profile-dropdown.tsx` — avatar trigger + DropdownMenu items
- `components/ui/avatar.tsx` — see Section B

**Modified:** `app/(app)/layout.tsx` removes inline header markup, mounts `<AppHeader />`.

**Error handling:**
- Logout failure → toast error, user stays signed in
- Auth missing somehow → header still renders; profile slot shows a "Sign in" link instead of the dropdown

### B. Profile pictures (PFP)

**Database migration** (new file in `lib/db/migrations/`):

```sql
ALTER TABLE profiles
  ADD COLUMN profile_picture_url text NULL,
  ADD COLUMN profile_picture_kind text NULL CHECK (profile_picture_kind IN ('static', 'gif'));
```

The tiny `profile_picture_kind` enum lets the Avatar component decide whether to wire up hover-swap without sniffing URLs (which is fragile — extensions can lie).

**Storage:**
- Bucket: `avatars` (Supabase Storage), public-read
- Paths: `<userId>/avatar.<ext>` for the primary file; `<userId>/avatar-poster.png` for the GIF first-frame
- RLS: user can `INSERT`/`UPDATE`/`DELETE` only their own folder; `SELECT` is public via CDN URL
- Each new upload overwrites the prior file at the same path (no orphan accumulation)

**Avatar component (`components/ui/avatar.tsx`):**

```tsx
type Props = {
  user: {
    id: string;
    username: string | null;
    email: string;
    profilePictureUrl: string | null;
    profilePictureKind: 'static' | 'gif' | null;
  };
  size: 'sm' | 'md' | 'lg';
};
```

Render rules:
- `profilePictureUrl` present, `kind === 'static'` → plain `<img>` tag
- `profilePictureUrl` present, `kind === 'gif'` → `<img>` with `src` initially set to the poster URL; hover/focus swaps `src` to the animated GIF; mouseleave/blur swaps back. `prefers-reduced-motion: reduce` always shows the poster.
- No `profilePictureUrl` → 1-character initial in a circle. Initial = first letter of `username` (or `email` if no username yet). Background color = deterministic palette pick from `hash(userId) % palette.length`. Palette is 8 pixel-art-friendly colors defined in `lib/design/avatar-palette.ts`.

**Upload flow:**

1. User on `/settings` → Profile section → clicks the avatar slot
2. Native file picker opens (accepts `image/jpeg, image/png, image/webp, image/gif`)
3. Client-side validation: type + size (≤ 5 MB) before any modal opens
4. Static images (jpg/png/webp) → `react-easy-crop` modal (drag, zoom, 1:1 aspect lock); GIFs skip the cropper
5. User confirms → server action `uploadAvatar(formData)`:
   - Re-validates auth, type, size server-side (client checks are convenience, not authority)
   - For GIFs: uses `sharp` to extract frame 0 as PNG → uploads `avatar.gif` AND `avatar-poster.png`
   - For static: uploads cropped result as `avatar.<ext>`
   - Updates `profile_picture_url` + `profile_picture_kind` in DB
   - Calls `revalidatePath('/', 'layout')` so the header avatar updates everywhere on next render (the header lives in `app/(app)/layout.tsx`, so layout-level revalidation is the cleanest way to refresh it across all authenticated routes). For Phase 1.5 scale this is appropriate; if it becomes a perf concern later, switch to tag-based revalidation with a `user-profile` tag on the user fetch.

**Settings page (new route `/settings`):**

- `app/(app)/settings/page.tsx` — section-based layout
- `app/(app)/settings/_sections/profile-section.tsx` — Phase 1.5 ships only this section: avatar uploader + username editor
- Future sections (Account, Privacy, Notifications) land when they have content

**New files:**
- `lib/db/migrations/000X_add_profile_picture.sql` (new migration; remember to strip the auto-generated `CREATE TABLE auth.users` clause per project gotcha)
- `app/(app)/settings/page.tsx`
- `app/(app)/settings/_sections/profile-section.tsx`
- `components/ui/avatar.tsx`
- `components/settings/avatar-uploader.tsx` (cropper modal + file input)
- `lib/profile/avatar-actions.ts` (`uploadAvatar` server action)
- `lib/storage/avatar.ts` (Storage helpers + first-frame extraction with `sharp`)
- `lib/design/avatar-palette.ts` (8-color initials palette)

**Modified files:**
- `lib/db/schema.ts` (add 2 columns to `profiles`)
- All sites currently rendering an avatar-shaped placeholder (replace with `<Avatar />`):
  - `app/(app)/u/[username]/page.tsx`
  - `components/layout/app-header.tsx` (header avatar)
  - any future profile-card uses

**New dependency:** `react-easy-crop` (~10 kB, MIT). `sharp` is already a Next.js peer dependency, no install needed.

**Error handling:**
- Client-side over-size or wrong-type → friendly inline error before modal opens; no upload attempt
- Server-side validation failure → form state shows the same friendly error
- Storage upload failure → keep current PFP, show toast
- DB update failure after successful upload → attempt to delete the just-uploaded file; show toast

### D. Username at signup + editing

**Shared validation schema** (`lib/profile/username-schema.ts`):

```ts
export const usernameSchema = z
  .string()
  .regex(/^[a-z0-9_]{3,24}$/, 'must be 3–24 chars, lowercase letters, digits, or _')
  .refine((v) => !RESERVED_USERNAMES.has(v), 'this name is reserved');
```

**Reserved-words blocklist** (`lib/profile/reserved-usernames.ts`):

```ts
export const RESERVED_USERNAMES = new Set([
  'settings', 'admin', 'login', 'signup', 'profile', 'library',
  'dashboard', 'home', 'u', 'games', 'api', 'auth',
]);
```

The set is referenced both by the schema and by any future route that needs to verify route-name safety.

**`<UsernameInput />` component** (`components/auth/username-input.tsx`):

Reused in signup form AND settings → Profile section. Behaviour:
- Controlled input
- 300ms debounce on user typing → calls server action `checkUsernameAvailability(value)`
- Inline status indicator under the field:
  - `…checking` (while debouncing or in flight)
  - `✓ @yourname is available`
  - `✗ already taken` / `✗ not allowed` / `✗ must be 3–24 chars, a–z, 0–9, _`
- Exposes a `valid: boolean` state to its parent so submit buttons can be enabled/disabled appropriately

**`checkUsernameAvailability` server action:**
- Validates the input against `usernameSchema` (returns `'invalid'` on failure)
- Checks reserved blocklist (returns `'reserved'`)
- Runs `select 1 from profiles where username = ?` (indexed) → returns `'taken'` or `'available'`
- Cheap; no rate-limiting needed for Phase 1.5 (single-user-ish portfolio scale)

**Signup flow update** (`app/(auth)/signup/page.tsx`, `actions.ts`):

- Form gets a username field above email/password, mounted on `<UsernameInput />`
- Submit button disabled until `username.valid && email.valid && password.valid`
- `signup` server action:
  - Re-runs `usernameSchema` server-side
  - Calls Supabase signup
  - Calls `ensureMyProfile({ username })` — passing the explicit username
  - Catches the unique-constraint violation on `profiles.username` (race condition) → returns `{ ok: false, error: 'taken', suggestions: ['yourname1', 'yourname_g', 'yourname_2'] }`
- Form renders the 3 suggestions as one-tap chips on race-condition error

**`ensureMyProfile` flow update** (`lib/profile/server-actions.ts`):

- Signature gains optional `username` arg: `ensureMyProfile(opts?: { username?: string })`
- If `username` provided → use it directly (signup path)
- If not → keep current email-prefix derivation (OAuth callback + idempotent re-entry path)
- Validates with `usernameSchema` before insert in either path

**Username editing in `/settings`:**
- ProfileSection mounts a second `<UsernameInput />` (live validation reused)
- New server action `updateUsername(newUsername)`:
  - Validates with `usernameSchema`
  - Runs availability check
  - `UPDATE profiles SET username = ?` (catches unique-constraint violation same as signup)
  - Calls `revalidatePath('/', 'layout')` (covers header) plus `revalidatePath('/u/[username]', 'page')` for both the old and new usernames so the username-bound profile route stays correct

**Existing users (you, with email-derived username):**
- No forced migration — current username keeps working as-is
- Editable any time from `/settings → Profile`. No "one-time" lock.

### E. Pure-implementation polish items

#### E2 — Heart visuals re-pixel

Re-author half-heart and full-heart sprites in `components/pixel/hearts.tsx` so the upper red fill is solid (currently reads as unfilled). Match palette and outline thickness against existing pixel sprites for visual coherence.

#### E3 — Performance pass (lands last)

Per the user's brief: profile + measure before optimizing. No code changes until measurements exist.

1. **Measure baseline** on `/library`, `/dashboard`, and quick-log palette open. Use Next.js `<Profiler>` wrappers + Chrome DevTools Performance tab. Record numbers.
2. **Investigate the three suspects:**
   - TanStack Query `initialData` always-stale refetch → likely fix `staleTime: 30_000` or similar
   - `next/image` `unoptimized={true}` on every cover → check whether RAWG image domains can go in `next.config.ts` `images.remotePatterns`
   - In-memory aggregation in `getUserStats` / `getRecentActivity` → check whether DB-side `COUNT(*) FILTER (WHERE status = ?)` outperforms fetch-all-rows-and-reduce
3. **Fix in priority order** (worst measurement first); re-measure; commit each fix as its own change so wins can be attributed
4. If a suspect turns out to be a non-issue at measurement, document that too

## Order of implementation

The plan in Step C will sequence these into bite-sized tasks. Recommended order:

1. **E1 Mapper-dedup** — first; no behavior change; simplifies later edits to `lib/logs/server-actions.ts`
2. **B foundation: Avatar component** (display only, accepts `imageUrl` prop); E2 hearts can land in parallel here
3. **A: AppHeader + NavTabs + MobileMenu + ProfileDropdown** (consumes Avatar)
4. **B: DB migration + Storage bucket + RLS**
5. **B: /settings page scaffolding + ProfileSection (avatar slot wired to existing Avatar)**
6. **B: AvatarUploader (cropper modal + server action + first-frame extraction)**
7. **D: UsernameInput component + checkUsernameAvailability action**
8. **D: Signup form integration + ensureMyProfile update**
9. **D: Username editing in /settings ProfileSection**
10. **C: View rename (Shelf/Stacks) + URL redirects**
11. **E3: Performance pass (measure → investigate → fix → re-measure)**

E1 and E2 are parallel-safe with each other. E3 lands last because profiling stabilized code is more meaningful than profiling code about to be refactored.

## Acceptance criteria summary

**Section A:** all authenticated pages show nav; mobile drawer opens/closes; active tab visually distinct; logout still works via dropdown.

**Section B:**
- Upload jpg/png/webp/gif ≤ 5 MB succeeds; over-size or wrong-type rejected with friendly error
- Avatar appears in nav and Profile page immediately after upload (revalidation works)
- GIF avatars show static frame at rest; animate on hover/focus only
- `prefers-reduced-motion: reduce` users always see the static frame
- Initials fallback works for users who haven't uploaded yet
- Editing PFP from /settings updates everywhere it's shown

**Section C:** view switcher labels read "Shelf" / "Stacks"; `/library?view=shelf` shows pixel-art grid; `/library?view=stacks` shows status carousels; default view = `shelf`; old `?view=grid` URL redirects cleanly.

**Section D:**
- Signup form rejects invalid/reserved/taken usernames live as user types
- Submit blocked until username is valid + available
- Race-condition collision at submit → friendly error + 3 suggestions
- Existing email-derived users can change username from /settings
- All username changes propagate (URLs + display everywhere update)

**Section E1:** `pnpm typecheck` + `pnpm lint` + `pnpm build` pass; manual gate verifies library, game detail page, modal, profile-page library all render the same as before.

**Section E2:** half-heart and full-heart visually distinct from empty-heart; upper half clearly filled with the red palette color.

**Section E3:** documented before/after numbers for the three flagged areas; if any are non-issues at measurement, that's documented too.

**Phase-1.5 gate (full):** all the above + `pnpm typecheck` + `pnpm lint` + `pnpm build` green; manual end-to-end gate from Phase 1 (the 14 checks) still passes; new manual checks for nav, avatar upload, hover-GIF, view rename, signup-username flow.

## Out of scope

- Display-name field separate from username (one-field design for Phase 1.5; can split later if a real need emerges)
- `/settings` sections beyond Profile (Account, Privacy, Notifications etc. land when they have content)
- `ActivityItem` mapper dedup in `getRecentActivity` — different shape, separate concern; flagged for future polish
- Cloudflare R2 / Images for avatars (Supabase Storage is sufficient at this scale)
- Avatar uploads at signup (only after, via `/settings`)
- Cropping for GIFs (server-side GIF re-encoding is its own complexity cliff; upload as-is is fine)
- One-time username locking (always editable per design decision)
- Phase 2 features (AI-first sub-features, social, etc.)
