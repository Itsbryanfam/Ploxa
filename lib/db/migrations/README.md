# Database migrations

This folder holds all SQL migrations applied to the live Supabase project. Most are generated by `pnpm drizzle-kit generate` from changes to `lib/db/schema.ts`; a handful are hand-authored when the change can't (or shouldn't) be expressed via Drizzle (e.g., partial indexes with predicate clauses, CONCURRENTLY operations, data backfills).

## Hand-authored index migrations: use `CREATE INDEX CONCURRENTLY` on hot tables

When you write a migration by hand that adds an index on a table the live app reads or writes frequently (`profiles`, `logs`, `reviews`, `comments`, `follows`, `likes`, `notifications`), use `CREATE INDEX CONCURRENTLY` rather than plain `CREATE INDEX`. Plain `CREATE INDEX` takes an `AccessShareLock` for the duration of the build, which briefly stalls reads on the target table.

`CREATE INDEX CONCURRENTLY` cannot run inside a transaction block, and Supabase's `mcp__supabase__apply_migration` wraps every migration in one. So the deployment shape is different:

```
# Drizzle-generated indexes + non-CONCURRENTLY DDL: still apply via apply_migration.
mcp__supabase__apply_migration name="00NN_description" query="<SQL>"

# Hand-authored CONCURRENTLY indexes: apply via execute_sql instead, which
# runs outside a transaction. Commit the .sql file alongside other migrations
# for documentation, but don't rely on apply_migration for it.
mcp__supabase__execute_sql query="CREATE INDEX CONCURRENTLY ..."
```

If a single migration mixes a CONCURRENTLY index with other DDL, split it into two files: the transactional bits (apply_migration) first, then the CONCURRENTLY index in its own file (execute_sql).

This rule is for **hand-authored** migrations. Drizzle's generated index DDL doesn't use CONCURRENTLY and the project is OK with that — Drizzle indexes ship alongside schema changes that already block the table. Don't post-process the Drizzle output to add CONCURRENTLY; the generated file should match `schema.ts` exactly so future diffs are clean.

## Existing migration audit (2026-05-14)

All 22 `CREATE INDEX` statements across migrations 0000–0013 were created without CONCURRENTLY:

- **Drizzle-generated** (0000, 0002, 0005, 0006, 0007, 0008): 19 indexes. Treated as accepted; the Drizzle convention is plain CREATE INDEX and we don't fork it.
- **Hand-authored** (0009 follows_followed_id_idx, 0010 comments_user_idx, 0013 profiles_deleted_at_idx): 3 indexes. All applied to prod when the rule wasn't yet documented; lock window already passed. Leaving in place — dropping and re-creating with CONCURRENTLY now would temporarily remove the index optimization for no benefit.

Future hand-authored index migrations should follow the rule above.

## Naming conventions

- Sequential 4-digit prefix matching Drizzle's auto-incrementer (`00NN_`). New hand-authored migrations should reserve the next number.
- Snake_case description after the prefix; keep it short but descriptive (`0009_follows_followed_id_idx`, not `0009_idx`).
- Drizzle's snapshot files in `meta/` are owned by the Drizzle CLI — don't hand-edit them. If a snapshot drifts (we've seen 0007–0011 missing on disk), add the SQL to a new numbered migration; don't rebuild the snapshots.

## Reference

- `mcp__supabase__apply_migration` — wraps query in a transaction, records in `_supabase_migrations` table.
- `mcp__supabase__execute_sql` — runs the query as-is, no transaction wrapper, doesn't appear in `_supabase_migrations`. Use for CONCURRENTLY index creation, vault secret writes, pg_cron schedule, and other non-transactional one-off operations.
- Postgres `CREATE INDEX CONCURRENTLY` docs: <https://www.postgresql.org/docs/current/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY>
